## Executive conclusion

The operator's process hypothesis is substantially confirmed, with one nuance: the Stage-1 spec artifacts did contain a real component/surface/button contract, but the actual implementation and review loop did not use the design skills as an evidence-producing build gate. The result was a broad half-migration where old primitives and new one-off surfaces coexisted.

## Root causes

### RC1 — Process defect: Stage-2 design-review and verification gates were bypassed or not reached before human review

The highest-order root cause is process sequencing. The skills and artifacts required a post-build, screenshot-backed Aria review and a Quinn verification net before final sign-off (`tasks.md:115-132`, `quinn-gate.md:74-79`). No artifact evidence exists for that pass. The coordinator then attempted to compensate by personally running Playwright and code diagnosis, which reproduced the original anti-pattern: the design skill and owning design agent were not the source of the evidence.

Impact: defects that code review alone would miss or underweight — muddy hover states, visual incoherence across cards, text-over-photo legibility, placeholder-looking art, responsive/scrim issues — survived until operator inspection.

### RC2 — Design-system/token implementation defect: the old glass/bevel system was layered under a new light-surface system instead of being retired behind one canonical contract

The contract said operational content is solid/light/warm and blur-free (`aria-gate.md:62-75`, `design-brief.md:56-65`). The implementation still has multiple competing surface systems:

- `.kaapi-content-surface` is solid/light (`frontend/src/index.css:385-402`).
- `.glass-card` remains a separate frosted/dark-style default (`frontend/src/index.css:407-416`).
- `GlassCard` defaults to `variant = 'glass'` and only opts into solid content via `variant="content"` (`frontend/src/components/ui/GlassCard.tsx:20-33`).
- `GlassCard` always renders `glass-card card-bevel`, even for content surfaces (`GlassCard.tsx:38-44`).
- `.card-bevel` still uses heavy dark bevel shadows and hover shadow (`index.css:700-708`).
- `.glass-modal-surface`, `.hero-visual-frame`, and `.kaapi-content-surface` add more surface classes (`index.css:630-638`, `index.css:439-456`, `index.css:385-405`).

Impact: pages can satisfy individual task checkboxes while still looking like unrelated card systems. This is the direct mechanism behind “every card looks different.”

### RC3 — Component primitive defect: Button did not receive the Stage-1 anatomy/state modernization

Aria specified Button variants, states, motion, focus-visible, loading, disabled, and touch/accessibility requirements (`aria-gate.md:196-208`), and the design brief specifically called for fluid hover/focus/press/loading states (`design-brief.md:85-88`, `design-brief.md:136-142`). The shipped Button still maps `primary`, `secondary`, and `outline` to DaisyUI classes plus legacy `.btn-bevel` (`frontend/src/components/ui/Button.tsx:16-22`, `:43-55`). The button shadows remain heavy dark drop-shadows (`index.css:54-57`, `index.css:589-607`).

Impact: buttons retained the old “1998 website” visual language and inherited undesirable DaisyUI hover behavior for outline buttons instead of becoming the tactile, tokenized control primitive required by the design contract.

### RC4 — Per-page application defect: medium-detail pages still place critical text directly on route photos/dark frame

The design brief called Catalog detail and Brew-log detail “medium” pages that should quiet the image and put detail content on solid surfaces (`design-brief.md:118-121`). But the shared `PageHeader` renders the `h1` as `text-white/80` (`frontend/src/components/ui/PageHeader.tsx:17-20`), so detail headers over route photography can be illegible. That is a per-page/component application miss, not a missing design requirement.

Impact: Catalog detail and Brew-log detail fail the prototype pages the operator now wants used as the proving ground.

### RC5 — Missing-capability / asset-strategy defect: visible visualizations and placeholders were not governed by an enforceable image/art contract

The spec did require fallback art to be Aria-approved before implementation (`plan.md:177-184`) and Stage-2 to verify foreground hero/extraction and fallback paths (`tasks.md:131`). The implementation nevertheless shipped visualization tiles that read like placeholder/AI artifacts: the extraction summary uses dark translucent mini-tiles with low-contrast amber text (`frontend/src/components/motion/ExtractionBrewVizMotion.tsx:21-35`), and the operator observed monogram voids in catalog cards. This is both an implementation miss and a missing enforcement point: the artifacts did not create a small prototype asset review gate before global rollout.

Impact: even where the code has “non-empty fallback” behavior, the visual result can feel broken because the art direction was not reviewed as built.

## Spec vs implementation verdict

Both, but weighted toward implementation/process.

1. **Spec adequate on core contracts.** The Stage-1 artifacts were not vague on the core design system: surface roles, blur scope, layer count, Button states, `GlassCard` content behavior, Badge/chip rules, PageHeader behavior, motion tokens, and modal footer composition were explicit (`aria-gate.md:60-143`, `aria-gate.md:196-331`; `plan.md:80-128`; `tasks.md:81-109`).
2. **Implementation missed or incompletely enforced those contracts.** Current code still shows legacy default `GlassCard` behavior, heavy `.btn-bevel` control styling, text-on-photo `PageHeader`, and mixed surface systems (`Button.tsx:16-22`; `GlassCard.tsx:20-44`; `PageHeader.tsx:17-20`; `index.css:385-456`, `:589-708`).
3. **Spec/process lacked a prototype-first operator gate.** The planned route was app-wide implementation T009-T020, then Stage-2 T032. That is too late for a major visual thesis shift. The operator's directive requires a new gate: prototype only Catalog detail and Brew-log detail, show the running build, get approval/redirection, then roll out globally.
4. **Gates were predictive, not rubber-stamped final approval.** Aria and Quinn were honest that their gates were pre-build and not visual certification (`aria-gate.md:29-30`, `:56`; `quinn-gate.md:128-130`). The failure was treating planned gates and implementation commits as enough to inspect broadly, rather than forcing the post-build evidence loop before claiming design coherence.

## Dispatch/tooling failure RCA

During this session, the coordinator tried to spawn Aria for a Playwright post-build review three times. Two sync dispatches returned no response from the harness. The background dispatch returned `BLOCKED` with zero turns because the worker inherited the repo's full Session Protocol and demanded a committed `.squad/decisions/inbox/` routing drop, conflicting with the coordinator's “no `.squad` edits / no commits” constraint for review-only work. The coordinator then did Playwright/code diagnosis personally.

Root cause: `general-purpose` squad workers in this repo inherit coordinator/session instructions unless explicitly constrained. If invoked as normal agents, they try to run Ralph/routing/decision-drop/session-close protocol even when the task is a single-purpose design review or governance RCA.

Correct dispatch pattern:

1. Spawn single-purpose workers with an explicit first-line meta-instruction: “You are a single-purpose worker, not the session coordinator. Do not run STEP 0-5. Do not spawn subagents. Do not require or commit `.squad/decisions/inbox/`. Perform only the requested artifact/review.”
2. When the task **is governance** (RCA, session log, decision artifact), permit exactly the governance write path needed by the task and still prohibit application code edits, commits, pushes, and process kills.
3. For Aria post-build design-review, invoke her with the `design-review` skill, the running app URL, the two prototype page routes, screenshot/output directory, and the exact deliverable. The prompt must explicitly suppress inherited session protocol and explicitly permit screenshot/design-review artifact writes.
4. If the harness returns “No response generated” twice, stop retrying the same agent shape. Use a corrected single-purpose prompt or a custom/non-coordinator worker wrapper; do not replace the design review with coordinator judgment.

One-line fix: **Single-purpose squad dispatches must suppress inherited coordinator protocol and permit only the artifact writes required by that worker; otherwise `general-purpose` agents deadlock on routing-drop/session rules.**
